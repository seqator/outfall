# Outfall — техническая архитектура

> Живой документ. Источник решений — `docs/planerka/01-concept/engine-architect.md`
> (первое предложение) и последующие ADR в `docs/tech/adr/`. Если решение
> расходится с планёркой — актуальный источник истины здесь и в ADR, планёрка
> остаётся историческим протоколом.

## 1. Слои и границы

```
core/   — чистый TypeScript. Тик, ECS-контейнер, шина событий, RNG, изометрия, математика.
sim/    — игровая симуляция: системы ECS (движение, бой, ИИ, квесты...).
game/   — оркестрация: сцены, склейка core/sim с render/audio/ui/input/assets.
render/ ui/ audio/ input/ assets/ — конкретные реализации на границе с DOM/Pixi.
```

Правило зависимостей: `core ← sim ← game → render, audio, ui, input, assets`.
`core` и `sim` не импортируют друг у друга ничего «наружу» и не трогают
`window`/`document`/`localStorage`/`fetch`/`requestAnimationFrame` — это
проверяется ESLint (`import-x/no-restricted-paths`, `no-restricted-globals`,
см. `eslint.config.js`). `pixi.js` — единственная тяжёлая рантайм-зависимость,
изолирована в `src/render/pixi/**`.

Почему так жёстко: команда — агенты-программисты, работающие параллельно и
короткими сессиями. Граница, которую проверяет линтер, не «дрейфует» между
задачами так, как дрейфует договорённость в документации.

## 2. Рендер: PixiJS 8 (WebGL)

Выбор и обоснование (сравнение с Canvas 2D и Phaser) зафиксированы в
`docs/planerka/01-concept/engine-architect.md` §1 и реализованы в OF-005.
Кратко: спрайт-батчинг и `ParticleContainer` дают запас 3–5× по FPS на
изометрии с 200+ спрайтами и частицами против ручного Canvas 2D; в отличие от
Phaser, Pixi не навязывает свой игровой цикл и объектную модель — `sim` и
`render` остаются независимыми слоями, что и требует §1 этого документа.

## 3. Игровой тик (OF-010, `src/core/loop.ts`)

- Частота симуляции — **60 Гц** (`TICK_HZ = 60`, `TICK_DT = 1/60`).
  Черновик планёрки предлагал 30 Гц; решение спринта — 60 Гц (см. константу и
  комментарий в коде), чтобы не удваивать проблему интерполяции на быстром
  экшене без запаса на будущее.
- `createLoop(sim, input, raf)` — аккумулятор фиксированного шага:
  `RafLike.request` даёт кадр с произвольным `timeMs`; излишек времени между
  кадрами копится в `accumulator` и досчитывается тиками по `TICK_DT`, пока
  не исчерпан либо остаток, либо бюджет `MAX_TICKS_PER_FRAME = 5`.
- Защита от «спирали смерти»: если долг тиков не удалось погасить за
  `MAX_TICKS_PER_FRAME` шагов (вкладка была свёрнута), остаток **сбрасывается**,
  а не переносится — иначе один долгий кадр порождал бы бесконечно растущую
  очередь тиков и кадр никогда бы не дорисовался.
- `onFrame(cb)` отдаёт `alpha = accumulator / TICK_DT ∈ [0,1)` — долю
  пройденного тика для интерполяции `prevX/prevY → x/y` в рендере (рендер сам
  не входит в скоуп OF-010, но контракт уже пригоден к использованию —
  см. OF-015).
- `RafLike` — абстракция над `requestAnimationFrame`, реализуется в `src/game`
  или `src/input`, а не в `core` (иначе `core` тронул бы `window`).
  Тестовый двойник — `tests/unit/core/support/fake-raf.ts`: полностью
  управляемое «время», без реальных таймеров.

## 4. ECS (OF-010, `src/core/world.ts` + `src/sim/`)

- `EntityId` — `index * 2^12 + generation`. При `destroy()` слот индекса
  освобождается и кладётся в пул повторного использования, а поколение
  увеличивается по модулю `2^12` — старый `EntityId` численно не совпадает с
  новым, значит устаревшая ссылка не «оживает» вместе с переиспользованным
  слотом без явной проверки `alive()`.
- Компоненты — **plain-объекты без методов**, регистрируются через
  declaration merging интерфейса `Components` (`core/world.ts`) из
  `src/sim/components/*`: каждая система приносит свой кусочек типа, не
  трогая `core`. Тот же приём применяется к `GameEvents` в `core/events.ts`.
- `World.store(key)` лениво создаёт `ComponentStore` на первое обращение и
  кэширует его по строковому ключу компонента; `World.query(...keys)`
  перебирает сущности наименьшего из перечисленных сторов и фильтрует
  остальные через `has()` — минимизирует количество проверок на «горячих»
  запросах с несколькими компонентами.
- `destroy(e)` удаляет сущность разом из всех существующих сторов —
  инвариант «мёртвая сущность не встречается ни в одном query()» не требует
  отдельной сборки мусора.
- Продвижение тика (`World.tick`) — отдельная возможность `WorldControl`
  (`advanceTick()`), которую видит только оркестратор симуляции
  (`sim.createSimulation`), а не отдельные системы: система получает `World`
  без права сдвинуть счётчик тика сама.
- `sim.createSimulation(world)` — реализация контракта `Simulation` из
  `core/loop.ts`: один `step(dt, input)` = прогон `SYSTEM_ORDER` → инкремент
  `world.tick` → `world.events.drain()`. Порядок важен: подписчики на события
  видят согласованное состояние мира, а не мир в процессе очередной системы.
- Первый пример по цепочке систем (`input → ai → movement → collision →
  combat → effects → quest → cleanup`, см. планёрку §3.2) — `input →
  movement`: `inputControlSystem` переносит `InputSnapshot.moveX/moveY` в
  `velocity` управляемых сущностей, `movementSystem` интегрирует `transform`
  из `velocity`. Остальные стадии добавляются задачами OF-015/016 и далее в
  `SYSTEM_ORDER`, в конец соответствующей стадии.

## 5. Шина событий (OF-010, `src/core/events.ts`)

`emit()` только кладёт событие в очередь; обработчики **не вызываются
синхронно во время тика**. `drain()` — обычно последний шаг `sim.step()` —
берёт снимок очереди, чистит её и только затем вызывает подписчиков. Если
обработчик сам вызывает `emit()`, новое событие уходит в очередь *следующего*
`drain()`, а не зацикливает текущий проход. Это делает порядок доставки
детерминированным и независимым от того, кто на что подписан.

## 6. Ввод и детерминированный реплей (OF-010, `src/core/input.ts`)

`InputSnapshot` — неизменяемые данные без DOM. `InputSource` (контракт в
`core/loop.ts`) отдаёт снимок на тик; реальная DOM-реализация — задача OF-015,
живёт в `src/input`. `createScriptedInput(sequence)` — воспроизводит заранее
записанную последовательность снимков (после конца — повторяет последний
кадр). Вместе с `createSeededRng` (`core/rng.ts`, mulberry32) это даёт
воспроизводимость: **тот же `seed` + та же записанная последовательность
инпутов ⇒ тот же результат симуляции**, что проверяется реплей-тестом
`tests/integration/replay.test.ts` (два независимых прогона дают идентичный
хэш состояния мира; хэш также зафиксирован литералом как регрессионный тест).

## 7. Тестируемость

- `core/` и `sim/` тестируются в Node без DOM (`vitest.config.ts`,
  `environment: 'node'`) — этому напрямую служит граница из раздела 1.
- Покрытие `src/core/**` и `src/sim/**` — 100% по строкам/веткам/функциям
  (см. `npm run test -- --coverage`). Несколько заведомо недостижимых через
  публичный API защитных веток (например, отсутствие компонента у сущности,
  уже отфильтрованной `query()` по этому же компоненту) помечены
  `/* v8 ignore next */` с комментарием-обоснованием — это осознанная защита
  инварианта ECS, а не забытый код.
- `NullRenderer` (`src/render/null-renderer.ts`, OF-005) — рендер без побочных
  эффектов для headless-прогонов `sim` в тестах/CI.

## 8. Данные и сохранения

Схемы контента (`ItemSchema`, `DialogSchema`, `MapSchema`...) и валидатор —
зона OF-009 (`src/data/schemas/**`, `tools/validate-data.ts`), не описываются
здесь. Сохранения (`SaveStore`, миграции) — зона OF-019. Контракты обеих
задач см. в `docs/planerka/01-concept/engine-architect.md` §3.7–3.8.
