# ADR-002: Фиксированный тик 60 Гц, минимальный ECS, шина событий после тика

- Статус: принято (OF-010).
- Источник: `docs/planerka/01-concept/engine-architect.md` §3.1–3.2, §3.9;
  реализация — `src/core/loop.ts`, `src/core/world.ts`, `src/core/events.ts`,
  `src/sim/**`.

## Контекст

Реалтайм-экшен с боем, ИИ, партиклами и позже — сохранениями/реплеями.
Требования: (1) детерминизм — «тот же `seed` + та же последовательность
инпутов ⇒ тот же результат», проверяемый тестом; (2) отделение симуляции от
кадровой частоты рендера (60+ FPS с интерполяцией); (3) ECS должен оставаться
тестируемым в Node без DOM; (4) команда — агенты, добавляющие компоненты и
системы в разных задачах (OF-015, OF-016, ...) — расширение не должно
требовать правок `core`.

## Решения

### 1. Частота тика — 60 Гц, не 30

Черновик планёрки предлагал `TICK_HZ = 30` (рендер 60+ с интерполяцией).
Решение спринта, зафиксированное уже в каркасе OF-005 и подтверждённое здесь:
**`TICK_HZ = 60`** (`TICK_DT = 1/60 с`). Причина: боевая система (OF-016)
целится в «читаемый и динамичный» бой без ощущения задержки ввода; на 30 Гц
разница между вводом и реакцией мира (до полутика = 33 мс) при быстром экшене
заметна, на 60 Гц (до 16.7 мс) — нет. Плата — вдвое больше вызовов `sim.step`
в секунду; при бюджете `sim ≤ 4 мс/кадр` (риск №3 бэклога) это не критично на
100+ сущностях, но требует контроля по мере роста контента (профилировать в
OF-016/028, не откладывать до полировки).

### 2. `GameLoop` — аккумулятор фиксированного шага с ограниченным догоном

`createLoop(sim, input, raf)`: на каждый кадр `raf` (произвольный `timeMs`)
накопленное время делится на тики по `TICK_DT`, пока не кончится либо
накопленное время, либо бюджет `MAX_TICKS_PER_FRAME = 5`. Если долг не
погашен за этот бюджет — **остаток сбрасывается**, а не переносится на
следующий кадр.

Альтернатива (не выбрана): переносить необработанный долг дальше. Отвергнута
— после сворачивания вкладки браузер копит один огромный `timeMs`-скачок; без
сброса это гарантированный «шторм тиков», который не даёт кадру
прорисоваться неопределённо долго (классическая «спираль смерти» игровых
циклов).

`RafLike` — абстракция над `requestAnimationFrame`, реализуется вне `core`
(в `game`/`input`), поэтому `core/loop.ts` не трогает `window`. Тестовый
двойник `tests/unit/core/support/fake-raf.ts` не планирует кадры сам — тест
явно вызывает `fire(timeMs)`, что даёт точный контроль над «временем» без
реальных таймеров и делает тесты аккумулятора мгновенными и детерминированными.

`onFrame(cb)` отдаёт `alpha ∈ [0,1)` — точка, где рендер интерполирует
`prevX/prevY → x/y` компонента `transform`. `frame()` дополнительно защищён
флагом `running` (не только `raf.cancel()`) — race guard на случай
ненадёжной реализации `RafLike` (см. тест «утёкший кадр после stop()»).

### 3. ECS: числовой `EntityId` с поколением, ленивые `ComponentStore`, declaration merging для `Components`

- `EntityId = index * 2^12 + generation`. При `destroy()` индекс уходит в пул
  переиспользования, поколение увеличивается по модулю `2^12`. Переиспользование
  индекса не воскрешает старые ссылки: старый `EntityId` численно отличается
  от нового на том же слоте.
  - Альтернатива (не выбрана): `EntityId` как непрозрачный объект/строка
    (UUID). Отвергнута — числовой id дешевле как ключ `Map`/сортировки и как
    поле в сериализуемых компонентах (важно для будущих сохранений, OF-019).
- `Components` (`core/world.ts`) — намеренно пустой публичный интерфейс,
  расширяемый **declaration merging** из `src/sim/components/*`
  (`declare module '../../core/world' { interface Components { ... } }`).
  Так `core` не знает о конкретных компонентах игры, а каждая система
  приносит свой тип, не трогая `core/world.ts`. Тот же приём применён к
  `GameEvents` (`core/events.ts`) для событий шины.
- `World.store(key)` создаёт `ComponentStore` лениво, по первому обращению, и
  кэширует по строковому ключу — не нужно заранее регистрировать все типы
  компонентов централизованно.
- `World.query(...keys)` перебирает наименьший из перечисленных сторов и
  фильтрует остальные через `has()` — на несбалансированных запросах (частый
  компонент + редкий тег) заметно дешевле полного перебора по первому
  попавшемуся ключу.
- `destroy(e)` проходит по **всем существующим** сторам и удаляет запись —
  инвариант «мёртвая сущность никогда не встретится в `query()`» не требует
  отдельного шага сборки мусора и не зависит от того, в каком порядке
  создавались компоненты и стор.
- Продвижение `World.tick` вынесено в отдельный интерфейс `WorldControl`
  (`advanceTick()`), который получает только `sim.createSimulation`, а не
  системы — система не может случайно (или намеренно, в обход `SYSTEM_ORDER`)
  сдвинуть тик мира.

### 4. Первый пример системы — `input → movement`

`SYSTEM_ORDER` (порядок стадий из планёрки: `input → ai → movement →
collision → combat → effects → quest → cleanup`) заполнен первым звеном:
`inputControlSystem` переносит `InputSnapshot.moveX/moveY` в `velocity`
сущностей с компонентом-маркером `controlled`; `movementSystem` интегрирует
`transform` из `velocity`, попутно фиксируя `prevX/prevY` для будущей
интерполяции в рендере. Это не боевая/AI-логика (вне скоупа OF-010) — только
эталон, по которому OF-015/016 добавляют свои стадии в конец массива.

### 5. `EventBus`: доставка строго после тика

`emit()` кладёт событие в очередь и не вызывает обработчики синхронно.
`drain()` — последний шаг `sim.step()` — забирает снимок очереди, **чистит
очередь до вызова обработчиков**, и только затем дозванивается подписчикам.
Если обработчик сам вызывает `emit()` во время `drain()`, новое событие уходит
в очередь следующего тика, а не обрабатывается в этом же проходе.

Альтернатива (не выбрана): синхронный `emit`, обработчики вызываются
немедленно. Отвергнута — порядок доставки тогда зависел бы от порядка систем
внутри тика и от того, кто на что успел подписаться раньше, что ломает
детерминизм реплея и усложняет отладку (аудио/UI реагировали бы на
полу-обновлённый мир).

## Последствия

- Реплей-тест (`tests/integration/replay.test.ts`) прогоняет
  `seed + InputSnapshot[]` через настоящие `GameLoop` + `Simulation` + `World`
  дважды и сверяет хэш итогового состояния; хэш дополнительно зафиксирован
  литералом как регрессия. Любое случайное изменение порядка выполнения
  систем, семантики `drain()` или арифметики тика — ловится тестом.
- `src/core/**` и `src/sim/**` покрыты тестами на 100% (строки/ветки/функции);
  несколько защитных веток, недостижимых через публичный API ECS (например,
  двойная проверка компонента внутри тела системы, когда `query()` уже
  гарантировал его наличие), помечены `/* v8 ignore next */` с обоснованием —
  явная защита инварианта, а не забытый код.
- Будущие задачи (OF-015 карта/коллизии, OF-016 бой) добавляют компоненты и
  системы, не трогая `core/loop.ts`/`core/world.ts`/`core/events.ts` — только
  `src/sim/components/*`, `src/sim/systems/*` и хвост `SYSTEM_ORDER`.
