# ADR-001: Рендер — PixiJS 8 за адаптером `IRenderer`

- Статус: принято (OF-005).
- Источник: `docs/planerka/01-concept/engine-architect.md` §1 (планёрка №1).

## Контекст

Изометрический реалтайм-экшен: 200+ спрайтов на экране одновременно, частицы
(кровь, искры, дым), требование — стабильные 60 FPS на среднем ноутбуке без
дискретной видеокарты (Intel Iris/UHD, 1080p). Игровая логика должна
тестироваться в Node, без DOM и без знания о конкретном рендере — команда
состоит из параллельно работающих агентов, и граница между слоями обязана
проверяться автоматически, а не держаться на дисциплине.

## Варианты

| Критерий | Canvas 2D | PixiJS 8 (WebGL) | Phaser 3/4 |
|---|---|---|---|
| Производительность на 200–500 спрайтов + 1–2k частиц | 40–55 FPS, просадки при overdraw; нужен ручной кэш тайлов в офскрин-канвасы | Спрайт-батчинг из одного атласа — единицы draw call; `ParticleContainer` — 10k+ частиц; запас 3–5× | Тот же WebGL-рендер, но выше накладные расходы на тяжёлую объектную модель `GameObject` |
| Контроль над кадром | Полный | Высокий: своя сцена, свой цикл, рендер по требованию | Низкий/средний: свой игровой цикл и сцены навязаны фреймворком |
| Размер бандла (min/gzip) | 0 | ~450 KB / ~130 KB (tree-shaking по подпакетам) | ~1.2 MB / ~330 KB, слабый tree-shaking |
| Тестируемость логики отдельно от рендера | Отличная, но требует дисциплины | Отличная: логика не знает о Pixi, адаптер читает компоненты и обновляет пул спрайтов | Плохая: логика естественно прилипает к `Phaser.Scene`/`Physics.Arcade` |
| Риск для агентной команды | Средний: агенты заново изобретают батчинг/атласы/камеру | Низкий: узкий API, чёткая граница «логика → адаптер» | Высокий: фреймворк диктует структуру, риск смешать симуляцию со сценами и потерять детерминизм |

## Решение

**PixiJS 8**, спрятанный за интерфейсом `IRenderer` (`src/render/renderer.ts`).
Единственное место в кодовой базе с `import 'pixi.js'` — `src/render/pixi/**`;
это гарантируется ESLint-правилом `no-restricted-imports`. Для тестов и
headless-сценариев (реплеи, интеграционные тесты `sim`) — `NullRenderer`
(`src/render/null-renderer.ts`), реализующий тот же интерфейс без побочных
эффектов.

Обоснование:
1. Единственный вариант из трёх, который даёт 60 FPS с запасом на
   интегрированной графике при 200+ спрайтах и частицах без самописного
   батчинга.
2. Pixi — библиотека, а не фреймворк: игровой цикл, сцены, ввод, данные и
   сохранения остаются нашими — это условие детерминированного тика с
   фиксированным шагом (см. ADR-002) и тестов в Node.
3. Если WebGL окажется недоступен или Pixi 8 создаст проблему — `IRenderer`
   формализует границу настолько, что Canvas 2D-реализация того же
   интерфейса возможна без переписывания игровой логики.
4. Phaser отвергнут: бандл ×2.5 крупнее, слабая тестируемость, и, главное —
   архитектурный конфликт (свой игровой цикл и объектная модель против нашего
   детерминированного `core/loop.ts`).
5. Чистый Canvas 2D отвергнут как основной путь: производительность на
   грани требований, а «горячий» код (батчинг, кэш тайлов) пришлось бы писать
   вручную — самый рискованный тип кода для агентной команды.

## Последствия

- `src/core` и `src/sim` не видят Pixi вообще (граница проверяется ESLint,
  `import-x/no-restricted-paths` + `no-restricted-imports`).
- Любой прогон `sim` (юнит/интеграционные тесты, реплеи) работает без
  реального рендера через `NullRenderer` — не требует браузера/canvas.
- Частицы (`fx:burst`) — чисто визуальная забота рендера: `sim` публикует
  событие через `EventBus` (см. ADR-002), рендер решает, сколько и как
  частиц породить. Симуляция не зависит от количества частиц на экране.
- Пиксель-арт требует `pixelArt: true` при инициализации (`RendererInitOptions`)
  — нет сглаживания текстур; это же ограничивает выбор фильтров Pixi
  (`filters` подпакет сознательно не тянется в бандл ради размера).
